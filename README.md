# ZBPM

**Движок бизнес-процессов, который исполняет модели Camunda 8 на вашем сервере — без лицензии и без переделки схем.**

Вы рисуете процесс (согласование отпуска, заявка на оборудование, проверка документов) в привычном редакторе
[Camunda Modeler](https://camunda.com/download/modeler/) и загружаете файл в ZBPM. Дальше система сама ведёт каждую
заявку по схеме: ставит задачи людям, вызывает ваши сервисы, ждёт сроков и сообщений, фиксирует всё, что произошло.

> **Статус:** рабочий движок, проверен под нагрузкой: 4 часа на трёх репликах — 12 265 процессов, все завершены,
> без инцидентов и перезапусков. Что не умеет и чем отличается от Camunda 8 — честно в разделе
> [«Границы»](#границы-что-мы-не-делаем-и-чем-отличаемся).

## 1. Для бизнеса: что это даёт

| Вам нужно | ZBPM делает |
|---|---|
| Чтобы заявка не терялась и шла строго по регламенту | Каждая заявка — «экземпляр процесса» с полной историей: кто, когда, что решил |
| Видеть, где застряло | Единый веб-интерфейс: схема процесса с подсветкой текущего шага, задачи, ошибки, переменные |
| Менять регламент без программистов | Схема — это файл. Новая версия загружается рядом со старой, идущие заявки доезжают по старой |
| Подключить существующие системы (1С, SAP, свои сервисы) | Сервис-задачи вызывают ваши сервисы через очередь сообщений или встроенный HTTP-вызов |
| Не зависеть от лицензий | Apache 2.0, свой сервер, свои данные |
| Не переучивать аналитиков | Тот же Camunda Modeler и те же схемы, что и в Camunda 8 |

**Как это выглядит на практике:**

```
Аналитик рисует схему ──▶ загружает файл ──▶ заявка стартует ──▶ задача сотруднику ──▶ вызов сервиса
   (Camunda Modeler)        в ZBPM            (форма / API)       (согласовал / нет)     (1С, SAP, HTTP)
                                                                        │
                                                      решение определяет, куда идти дальше ──▶ готово
```

## 2. Словарь (чтобы говорить на одном языке)

| Термин | Что это |
|---|---|
| **Процесс (определение)** | Схема в формате BPMN 2.0: шаги и стрелки между ними. Файл. |
| **Экземпляр процесса** | Одна конкретная заявка, идущая по схеме. |
| **Пользовательская задача** | Шаг, где нужен человек: согласовать, заполнить, проверить. |
| **Сервисная задача** | Шаг, который выполняет программа: вызвать сервис, посчитать, отправить письмо. |
| **Воркер** | Программа, которая берёт сервисные задачи нужного типа и выполняет их. |
| **Шлюз** | Развилка: по условию идти одним путём, несколькими или ждать всех. |
| **Multi-instance** | Один шаг (или подпроцесс), повторённый для каждого элемента списка: например, согласование каждым из N руководителей. |
| **Инцидент** | Шаг не смог выполниться после всех повторов. Процесс стоит и ждёт, пока человек разберётся и нажмёт «повторить». |
| **FEEL** | Язык выражений Camunda для условий и вычислений (`amount > 1000`, `some r in results satisfies r = "OK"`). |

## 3. Что умеет

- **Схемы BPMN 2.0:** события (старт, таймеры, сообщения, сигналы, ошибки, эскалации), все виды шлюзов, подпроцессы,
  вызов другого процесса, **multi-instance** (параллельный и последовательный, с досрочным выходом), компенсация,
  транзакции, DMN-таблицы решений. Полная матрица — [docs/reference/bpmn-support.md](docs/reference/bpmn-support.md).
- **Люди и системы:** задачи людям (по исполнителю, группе, форме) и сервисные задачи для программ.
- **Надёжность:** ошибки не теряются — повторы, затем инцидент с понятным текстом и ручным «повторить».
- **Интерфейс:** один веб-интерфейс вместо трёх (Operate/Tasklist/Cockpit), обновляется в реальном времени.
- **Масштабирование:** несколько одинаковых реплик за балансировщиком, один PostgreSQL; таймеры и задачи срабатывают
  ровно один раз на кластер.
- **Безопасность:** вход по логину и паролю, роли, API-ключи для интеграций, ограничения по владельцу процесса.

## 4. Для разработчиков: как устроено

```
 Браузер (SPA) ──HTTP + SSE──▶ ┌──────────────── ZBPM (Spring Boot, stateless реплики) ─────────────────┐
 Внешние системы ──REST──────▶ │  REST API ─▶ Движок: токены по графу, скоупы переменных, FEEL,          │
                               │              таймеры, инциденты, версионирование                          │
                               │      │                                                                    │
                               │      ├──▶ PostgreSQL  состояние, история, outbox событий                  │
                               │      └──▶ RabbitMQ ──▶ воркеры (ваши сервисы, встроенный HTTP-коннектор)  │
                               └───────────────────────────────────────────────────────────────────────────┘
```

**Главные идеи:**

1. **Состояние только в БД.** Движок ничего не держит в памяти JVM, поэтому реплики взаимозаменяемы, а рестарт безопасен.
2. **Токены по графу.** Экземпляр обходится токенами; параллельные ветки, подпроцессы и multi-instance имеют свои
   **скоупы переменных** (ближайший скоуп побеждает, выражения читают видимые переменные токена).
3. **Асинхронная работа через очередь.** Сервисные задачи уходят воркерам через RabbitMQ и возвращаются событием
   завершения/ошибки. Ошибка воркера: повторы → инцидент.
4. **События наружу — через outbox.** Любое изменение публикуется надёжно (AMQP, HTTP-pull или SSE для браузера).

**Модули** (многомодульный Maven):

| Модуль | Ответственность |
|---|---|
| `zorrobpm-contract` | Контракт REST API и модели данных |
| `zorrobpm-engine` | Ядро: разбор BPMN, исполнение, хранение, таймеры, инциденты |
| `zorrobpm-rest` | REST-контроллеры |
| `zorrobpm-rabbitmq` / `zorrobpm-exchange` | Обмен с воркерами и доменные события |
| `zorrobpm-job-handler-spring-boot-starter` | SDK для своих воркеров |
| `zorrobpm-http-connector` | Встроенный HTTP-коннектор (`io.camunda:http-json:1`, `zorrobpm:http`) |
| `zorrobpm-client` | Java-клиент к API |
| `zorrobpm-app` | Запускаемое приложение |
| `zorrobpm-frontend` | Веб-интерфейс (Vue 3 + TypeScript) |
| `zorrobpm-test` | Общие тестовые помощники |

**Стек:** Java 21 · Spring Boot 4.0.6 · PostgreSQL 16 · RabbitMQ 4.1 · Liquibase · Camunda FEEL · Vue 3 · nginx.

## 5. Быстрый старт (5 минут)

Нужны Docker и Docker Compose.

```bash
git clone https://<internal-git-host>/ismet/microservices/zorro-bpm/zbpm.git
cd zbpm
cp .env.example .env
docker compose up -d --build
```

| Что | Адрес |
|---|---|
| Веб-интерфейс | http://localhost:8081 |
| API и Swagger | http://localhost:8080/swagger-ui.html |
| RabbitMQ (управление) | http://localhost:9300 |

Первый вход: `admin` / `admin` — **сразу смените пароль и `ZORROBPM_JWT_SECRET`** перед любым использованием вне
локальной машины ([безопасность](docs/reference/security.md)).

**Первый процесс:** нарисуйте схему в Camunda Modeler → в интерфейсе нажмите «Загрузить процесс» → «Запустить».
Через API:

```bash
curl -X POST http://localhost:8080/process-definitions -H 'Content-Type: application/json' \
  -d "{\"bpmn\": $(jq -Rs . < my-process.bpmn)}"
curl -X POST http://localhost:8080/process-instances -H 'Content-Type: application/json' \
  -d '{"processDefinitionKey":"my-process","variables":[{"name":"amount","type":"LONG","value":"100"}]}'
```

(в боевой конфигурации запросы требуют `Authorization: Bearer <токен>`; подробности и все эндпоинты —
[docs/reference/rest-api-and-client.md](docs/reference/rest-api-and-client.md)).

## 7. Совместимость с Camunda 8

**Цель:** исполнять те же BPMN/DMN-модели, что и Camunda 8, без правок файлов. Измеряем по двум осям:

- **Элементы BPMN** — поддержаны практически все конструкции, которые исполняет Zeebe.
- **Расширения `zeebe:*`** — реализовано 23 из 26 типов (88 %); три оставшихся — сознательный отказ
  (привязка RPA-ресурсов, AI-агенты Camunda 8.8+).

**Чем сверяемся:** поведение — **живыми прогонами Camunda 8.5** (Zeebe 8.5.0), а не чтением документации; дизайн и
спецификация — документация **Camunda 8.9**. Расхождения между ними и с нами фиксируются в матрицах, а не прячутся.

**Совместимость на уровне моделей, а не протокола:** ваши `.bpmn` и `.dmn` переносятся; Zeebe-клиенты (gRPC) — нет,
воркеры пишутся под наш контракт. Подробности, известные расхождения и измерения —
[docs/reference/camunda8-compatibility.md](docs/reference/camunda8-compatibility.md).

## Границы: что мы не делаем и чем отличаемся

- **Нет распределённого брокера с партициями** (как у Camunda 8): один PostgreSQL, несколько stateless-реплик. Нагрузка
  подтверждена, но шардинга нет.
- **Нет gRPC-протокола Zeebe:** воркеры работают через REST и RabbitMQ.
- **Нет Optimize** (аналитики): вместо Operate/Tasklist/Optimize — один встроенный интерфейс.
- **Условия на потоках вне шлюзов не вычисляются** (так же, как в Zeebe): условие читается только на выходах из
  exclusive/inclusive шлюзов.
- **Известные расхождения с Camunda 8.5:** граничные события на multi-instance срабатывают на каждом инстансе (в Zeebe —
  на теле целиком); `completionCondition` пишется только дочерним элементом (атрибут игнорируется, как в Zeebe);
  строка с JSON-текстом не превращается в список — тип переменной должен быть `JSON`; строки в FEEL только в двойных
  кавычках.
- **HTTP-коннектор по умолчанию не ходит на приватные адреса** (защита от SSRF); для внутренних сервисов нужен
  осознанный выбор — см. [guide](docs/guides/http-connector.md).

## 9. Разработка

```bash
mvn clean verify                       # backend: unit + интеграционные на H2
bash ci/run-pg-tests.sh                # PG-набор на настоящем PostgreSQL (нужен Docker)
bash ci/run-rabbit-tests.sh            # интеграция с RabbitMQ
cd zorrobpm-frontend && npm test && npm run test:browser && npm run build
```

Нужны JDK 21, Maven 3.9+, Node 22 (для фронтенда). Подробно — [docs/reference/testing.md](docs/reference/testing.md).

**Что важно знать разработчику:**

- Интеграционный тест подхватывается CI только если класс называется `*IntegrationTests` (или `*PgIT` / `*ChaosIT`);
  имя `*IT` не запускается нигде.
- Поведение BPMN проверяется тем, **что осталось после** завершения (живые активности, токены, таймеры), а не только
  «процесс завершился».
- Поведение, определённое Camunda 8, сверяется живым прогоном Camunda 8.5 (раннер — `docs/analysis/c8-oracle/`).
- Решения по архитектуре — [docs/adr/](docs/adr/).
