# Авторизация и безопасность

> Вход в UI, API-ключи, роли, настройки безопасности. Вход в документацию — [README](../../README.md), карта — [docs/README.md](../README.md).

## Авторизация веб-консоли (UI)

Простой self-contained вход в UI по логину/паролю (без Keycloak):

- Аккаунты — в таблице `ui_users` (логин, PBKDF2-хэш пароля, роль `SUPER_ADMIN`/`ADMIN`/`USER`).
- `POST /auth/login` `{username,password}` → выставляет **httpOnly-cookie** `zbpm_token` (access, подпись HMAC-SHA256) + `refresh_token`; SPA ходит по cookie-сессии, программные клиенты — `Authorization: Bearer <token>`.
- **Refresh + ревокация** (`POST /auth/refresh`, `/auth/logout`) — короткий access + ротация refresh с детекцией повторного использования.
- **Rate-limit** на `POST /auth/login` (защита от brute-force).
- **API-ключи для интеграций** — service accounts аутентифицируются статическим ключом `Authorization: Bearer zbpm_sk_…` (без refresh; хранится как SHA-256, ревокация — kill-switch). Для машин (воркеры, 1С, SAP, боты).
- `GET /auth/me` — текущий пользователь (нужен валидный токен/ключ).
- `GET/POST/PUT /users` — управление пользователями (требует роль `ADMIN`/`SUPER_ADMIN`).
- При первом старте создаётся админ **`admin` / `admin`** (если таблица пуста) — **обязательно смените пароль** (в проде задайте `zorrobpm.security.default-admin-password`).

Конфигурация (env / `application.properties`):

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `zorrobpm.security.jwt-secret` | dev-секрет | секрет подписи токена — **обязательно переопределить в проде** |
| `zorrobpm.security.jwt-ttl-minutes` | `720` | срок жизни токена |
| `zorrobpm.security.require-api-auth` | `true` | защищать ли Data-API токеном (отключить только при наличии внешнего шлюза) |
| `zorrobpm.security.default-admin-username` | `admin` | имя сид-админа |
| `zorrobpm.security.default-admin-password` | `admin` | пароль сид-админа при первом старте |

> По умолчанию **все** эндпоинты (`/process-*`, `/user-tasks`, `/incidents`, …) требуют валидный `Authorization: Bearer <token>`. Отключить можно через `zorrobpm.security.require-api-auth=false` — только при наличии аутентифицирующего шлюза перед сервисом.

## Политика DMN evaluate — «чтение определения»

`POST /dmn/{decisionId}/evaluate` — **чистая функция над переданными переменными**. Эндпоинт читает опубликованное ОПРЕДЕЛЕНИЕ решения (строку `dmn_definitions`) и считает таблицу решений в FEEL. Данные инстансов он **не читает и не пишет**: во входе нет ссылки на инстанс, а `DmnService.evaluate(decisionId, variables)` ходит только в `dmn_definitions`. Оценка чужого решения над своими переменными не раскрывает чужих данных.

Кто может вызвать (решение maintainer 2026-10-21, аудит F-21):

| Кто | Что видит | Ответ |
|---|---|---|
| `UserPrincipal` — обычный аутентифицированный пользователь, в том числе **не участник** процесса | все **определения** (ADR-8 §1) | `200` + результат |
| `ServicePrincipal` — API-ключ | определения в пределах грантов: та же резолюция, что `readableRuntimePdIds` | `200` + результат; без гранта на процесс-владелец решения — `404` (существование решения скрыто) |
| `SUPER_ADMIN` | всё | `200` + результат |
| без аутентификации | — | `401` |

Почему определения видны всем, а runtime-данные — нет: ADR-8 §1 («видит все процессы» = **только определения** — BPMN, схема, версии; экземпляры, переменные, задачи и инциденты чужих процессов пользователю не видны). `GET /dmn` и `GET /dmn/{id}` следуют той же политике.

Что ограничивает саму оценку: rate-limit (`/dmn` — DATA-бакет) и лимит размера запроса (5 МБ, `DeployDmnDTO.MAX_DMN_LENGTH`). Политика закреплена тестом `DmnEvaluatePolicyIntegrationTests` (модуль `zorrobpm-rest`) и описана в Javadoc `DmnResource.evaluateDecision`.

## Модель доверия канала завершений (воркеры)

> Раздел модели угроз: что общий канал завершений позволяет, что не позволяет и при каких
> эксплуатационных условиях это допустимо. Решение по модели — maintainer,
> [`docs/internal`](../../docs/internal) (F-14).

### Как устроен канал

- **Один общий exchange.** Все воркеры публикуют результат в direct-exchange
  `zorrobpm.completions` (`zorrobpm-rabbitmq/.../configuration/RabbitConfiguration.java:45`).
  Routing key = имя очереди; биндинги объявляет движок — их три: основная очередь
  завершений, poison-парковка и очередь отложенной повторной доставки. Воркер выбирает
  routing key, то есть может положить сообщение в любую из этих трёх очередей, — но не в
  job-очередь: у неё своего exchange'а нет.
- **Приём без сверки отправителя.** Движок читает `serviceTaskId` из тела сообщения и
  ищет задачу по этому id (`zorrobpm-rabbitmq/.../ServiceTaskListener.java:67`). Кто
  именно опубликовал сообщение — не проверяется: **любой, кто может писать в этот
  exchange, может прислать результат по любому `serviceTaskId`.**
- **Раздача — по типу джобы.** Движок отдаёт задание в очередь `zorrobpm.jobs.<jobType>`
  (`zorrobpm-rabbitmq/.../JobQueueDeclarer.java`), где `jobType` — тип job'а из BPMN.
  Потребителей может быть много, они конкурируют, и **брокер не сообщает публикатору,
  кто именно взял задание**.
- **В сообщении нет личности отправителя.** Тело completion'а
  (`zorrobpm-exchange/.../ServiceTaskCompleteData.java`) несёт `serviceTaskId`, статус,
  текст ошибки, переменные и технические поля (`dispatchPhase`, `dispatchIndex`,
  `completionId`) — логина воркера там нет; AMQP-заголовки, которые читает движок, тоже
  его не несут.

### Что из этого следует

Движок **не может атрибутировать** completion к воркеру: он не знает, кто получил
задание, и не знает, кто прислал результат. Поэтому вопрос «завершил ли задачу тот
воркер, которому её выдали» движок себе задать не может — в принципе, а не из-за
недосмотра.

Вопрос, который движок **может** себе задать: «соответствует ли эта completion какой-нибудь
задаче, которую движок выдавал воркеру?». Это и проверяет
`zorrobpm-engine/.../trust/CompletionTrustMonitor.java` (на живом пути приёма
AMQP-completion'ов, до применения результата):

| Причина | Что означает | Что делает движок |
|---|---|---|
| `unknown_task` | такого id движок никогда не создавал | completion не находит задачу → приём падает, сообщение уходит в ретрай/DLQ |
| `no_job_issued` | задача создана, но джобу под неё воркеру **не выдавали** (нет строки `service_tasks` и открытой listener-фазы) | результат поглощается guard'ом движка; completion по user task не завершает её |

Счётчик — `zbpm.completion.unissued{reason="unknown_task|no_job_issued"}` (Prometheus),
плюс WARN-строка в логе движка. Считаются **попытки приёма**, а не уникальные
completion'ы: сообщение, которому движок не смог подобрать задачу, контейнер
переигрывает.

**Чего мониторинг НЕ покрывает** (важно для интерпретации): completion, пришедшая по
задаче, которую движок выдавал **другому** воркеру того же типа джобы, неотличима от
корректной — обе приходят на один exchange, в общий routing key, без указания
отправителя. Такой класс аномалий требует изменения протокола (см. следующий раздел) и
в рамках текущей модели не детектируется.

### Эксплуатационные условия, при которых модель считается рабочей

1. **Брокер — внутри доверенного периметра.** Доступ к RabbitMQ не должен быть из
   публичной сети; management API и AMQP-порт закрыты от внешних.
2. **Все воркеры — свои и доверенные.** Внешние/сторонние консьюмеры к каналу
   завершений не подключаются (см. триггеры пересмотра).
3. **Креды — per-worker, с минимальными правами.** Права воркера выдаёт движок
   (`zorrobpm-engine/.../RabbitMqProvisioningService.java:286`): `write` — только на
   `^zorrobpm\.completions$` (не на `amq.default`: право на default exchange открыло бы
   запись в любую очередь), `read` — на очереди job'ов этого воркера, их DLQ и на
   poison-очередь, `configure` — на объявление своих очередей. Юзер без членства ни в
   одном процессе получает deny-all (в т.ч. `write`).
4. **Ротация кредов.** Пароль брокера выдаётся по запросу оператора и не хранится в
   платформе; при компрометации учётной записи воркера меняется пароль и права
   пересобираются.
5. **Учётная запись самого приложения отдельно.** Движок работает под своим
   broker-аккаунтом; права воркеров ему не наследуются.

### Триггеры пересмотра модели

Модель пересматривается, если выполняется хотя бы одно условие:

- к каналу завершений подключён **сторонний (не наш) воркер** или воркер, права которого
  выданы вне платформы;
- **брокер выходит из доверенного периметра** (публичный endpoint, managed-RabbitMQ в
  чужом облаке, доступ из интернета);
- меняется **топология выкатки** (брокер переезжает, появляется публичный gateway перед
  management API);
- в движок приходит **версия, которая штампует идентичность вызова** (например,
  включён `zorrobpm.engine.dispatch-phase-stamping`) — тогда появляется основание для
  проверки «это результат именно того вызова»;
- в канал завершений начинает писать **кто-то, кроме воркеров** (сторонний сервис,
  скрипт, ручной `rabbitmqadmin`).

### Варианты на будущее (не реализованы)

Краткая оценка влияния на контракт — в отчёте
[`docs/internal`](../../docs/internal) (§5).
Коротко: per-worker очередь/routing меняет **протокол выдачи и приёма** (каждый воркер
получает свою очередь и свой routing key — правка стартера воркера, движка и
`RabbitMqProvisioningService`), подпись completion-токена при выдаче job меняет **тело
задания** (новое поле + проверка на приёме, у всех воркеров). Оба варианта — с
flag-day и миграцией; ни один не входит в текущую модель.
