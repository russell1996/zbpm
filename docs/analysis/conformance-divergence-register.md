# Реестр корней расхождений конформности Camunda 8 — вход в Ф4 (баг-WO по одному на корень)

WO-OPS-30, фазы Ф1 (FEEL/ioMapping), Ф2а (протокол job), Ф2б (HTTP-коннектор), Ф2в
(сообщения/script/DMN). **Сводный реестр:** каждый корень расхождения, измеренный на **живом**
Camunda/Zeebe 8.5 против нашего движка, с **глобально уникальным** идентификатором.

Зачем этот файл: в отчётах фаз корни пронумерованы **внутри каждой фазы** (`R1` есть и в Ф2а, и
в Ф2б, и в Ф2в) — при нарезке баг-WO «по одному на корень» такие номера **коллидируют**: «R4»
из Ф2а — это бюджет попыток, «R4» из Ф2б — `resultVariable`, «R4» из Ф2в — буферизация сообщений.
Здесь идентификатор **глобальный** (`JOB-R1`, `CONN-R7`, `MSG-R4`, `FEEL-R1`), так что один корень =
одна строка = одно баг-WO.

**Корень** = одна причина расхождения, а не один кейс. Один корень может накрывать несколько кейсов
(колонка «Кейсы»), и наоборот — несколько корней могут жить в одном кейсе.

**Где смотреть подробности:** каждая строка ссылается на источник — матрицу фазы и/или раздел
отчёта. Полные наблюдения (обе стороны) — в матрицах:
`docs/analysis/feel-iomapping-conformance-matrix.md`,
`docs/analysis/job-protocol-conformance-matrix.md`,
`docs/analysis/http-connector-conformance-matrix.md`,
`docs/analysis/message-conformance-matrix.md`.

**Статусы строки:**
* `Ф4` — корень уходит в баг-WO (расхождение с живым 8.5, которое мы чинить хотим).
* `by design` — наше осознанное отличие, баг-WO не заводим (зафиксировано, чтобы не переоткрыть).
* `решение владельца` — продуктовое решение нужно до того, как что-то чинить.
* `заведено` — по корню уже есть баг-WO (номер указан).

**Кампания баги НЕ чинит** (WO-OPS-30, Ф4): этот реестр — вход для нарезки баг-WО, а не список
правок.

Про Ф1: семь из восьми корней **уже заведены** баг-WO (C8-53…C8-56, C8-58) — их заново не
заводим, они в Ф4 не идут; `FEEL-R8` закрыт решением WO-ENG-33. То есть по Ф1 в Ф4 попадает
**ноль** корней — Ф1 уже разобран.

Про Ф2б: `CONN-R2` и `CONN-R4` в матрице помечены «by design», но с пометкой «продуктовое
решение» — в реестре они отнесены к `решение владельца`, потому что это **решение, а не
зафиксированное отличие**: пока владелец не сказал, строки могут уйти в `Ф4`.

Про Ф2в: из трёх корней в `Ф4` идёт только `MSG-R1` (тело задания); `MSG-R2` (DMN) и `MSG-R4`
(буферизация/TTL) — продуктовые решения, а не баги.

## Ф2в — сообщения, script, DMN

Источник: `docs/internal` §4; матрица
`docs/analysis/message-conformance-matrix.md`.

| ID | Корень | Кейсы | Живой Zeebe 8.5 | У нас | Статус | Куда |
|---|---|---|---|---|---|---|
| `MSG-R1` | Тело задания: снимок на диспетчеризации против переменных скоупа на активации | `f2v-msg-boundary-noninterrupting` | задание читает переменные скоупа **в момент активации** | тело задания — **снимок на момент диспетчеризации**; переменная, изменившаяся после постановки в очередь, до воркера не доезжает | Ф4 | баг-WO (тело задания) |
| `MSG-R2` | DMN: вызов решения | `f2v-dmn-called` | модель с `zeebe:calledDecision` принимается, но решение **не вычисляется** (инстанс стоит) | DMN вычисляется (`decision=20` при `amount=21`) | решение владельца | **продуктовое решение**: в 8.9 DMN-вызов есть — это наша сверх-возможность, а не дефект; решаем, нужна ли фича |
| `MSG-R4` | Буферизация сообщений (TTL) | `f2v-msg-buffered-catch` | сообщение с `timeToLive>0`, опубликованное ДО открытия catch-подписки, **буферизуется и доставляется** | параметра `timeToLive` в API публикации нет; буфера нет — сообщение теряется, инстанс ждёт на catch | решение владельца | **продуктовое решение**: нужна ли семантика «сообщение до открытия подписки не теряется» (тогда — TTL + буфер) |

> **Почему у `MSG-R4` нет `MSG-R3`.** Нумерация Ф2в продолжает нумерацию Ф2б (корни Ф2в ссылаются на
> общие для коннектора и сообщения `R1`/`R2`/`R4` из Ф2б — те же «тело задания»/`DMN`/`буфер»).
> В этом реестре идентификаторы **не наследуются**, а выдаются заново и глобально уникально, поэтому
> пропуска `MSG-R3` здесь нет. Аналогично в Ф2а/Ф2б нумерация своя.
>
> **Про контрольные кейсы `MSG-R4`.** В отчёте Ф2в §4 этот корень опирается на три кейса:
> `f2v-msg-buffered-catch` (расходится) и два **контрольных** — `f2v-msg-publish-before-deploy` и
> `f2v-msg-buffered-start-key` (обе стороны `match`: у 8.5.9 буфера для message start нет вовсе, и
> без ключа, и с ключом). В колонке «Кейсы» стоит **только расходящийся** кейс — контрольные
> перечислены в тексте отчёта и в матрице; их совпадение измеряет **границу** буфера, а не
> расхождение.

|---|---|---|---|---|

## Как читать этот реестр при нарезке баг-WО (Ф4)

1. **Одна строка = одно баг-WО.** Берём строки со статусом `Ф4`; для строк `решение владельца`
   сначала нужно решение (оно может превратить строку в `Ф4` или в `by design`).
2. **Идентификатор строки — это ID корня в баг-WО.** `JOB-R4` в баг-WО должен остаться `JOB-R4`,
   чтобы отчёт о правке ссылался на ту же строку реестра.
3. **Кейсы в строке — это готовый RED-набор** для баг-WО: строки матрицы соответствующей фазы уже
   содержат обе стороны (`8.9 docs | живое 8.5 | ours`) и вердикт, а измерительный корпус лежит в
   `*-cases.json` рядом с harness'ом. Баг-WО может ссылаться на них, не измеряя заново.
4. **Правки в движке — не в этой кампании.** Кампания меряет; чинит красная команда по баг-WО.
   После фикса строка реестра переводится в `match` в матрице фазы (как это уже сделано для
   `FEEL-R1`…`FEEL-R7` в матрице Ф1 — там строки помечены «`match` после фикса …»).
5. **Чего гейт НЕ делает.** `bash ci/wo-report-gate.sh WO-OPS-30` про реестр ничего не знает: он
   проверяет наличие доказательств в отчёте и существование названных тестов, но **не** сверяет
   реестр с матрицами фаз. Согласованность «каждая `ours differs`-строка матрицы покрыта реестром и
   у каждого корня ровно одна строка» проверяет скрипт
   `docs/analysis/check-divergence-register.js` (запуск — `node docs/analysis/check-divergence-register.js`;
   на текущем дереве — `Реестр: 30 корней; матрицы: 32 строк 'ours differs'` → `OK`). Скрипт проверен
   мутацией: у корня убраны кейсы → скрипт падает с перечислением непокрытых кейсов; после
   восстановления — снова `OK`. Проверку этой сверки **в CI** (чтобы реестр не разъехался с матрицами
   незаметно) — отдельная задача: гейт править нельзя (зона maintainer), а мой скрипт живёт в `docs/`, а
   не в сборке.
