# Мультитенантная авторизация: клиенты, API-ключи, изоляция процессов

Цель: ввести понятие **клиента** (системы-арендатора). Клиент создаёт/редактирует **только свои**
process definition и работает только со своими данными выполнения. Аутентификация клиента — по
**API-ключу**. Никто, кроме владельца, не видит и не трогает чужие модели/инстансы.

Документ — архитектура + примерный план работ. Кода нет.

---

## 1. Принципалы (кто обращается к системе)

Два типа, оба резолвятся в единый **TenantContext** `{ clientId, principalType, role }`:

1. **Client (система)** — внешняя интеграция. Аутентификация: **API-ключ** (`Authorization: Bearer zbpm_<...>` или `X-API-Key`). Всегда привязан к одному `clientId`.
2. **UI-user (человек)** — вход в консоль (уже есть: `ui_users` + JWT). Расширяем: у пользователя необязательный `client_id`:
   - `client_id = NULL` + роль `ADMIN` → **супер-админ** (видит всё, управляет клиентами/ключами);
   - `client_id = X` → оператор арендатора X (видит только данные X).

> Так и API-клиент, и человек дают одинаковый `clientId` — дальше вся изоляция работает единообразно.

---

## 2. Модель тенантности (кто чей)

**Владелец — process definition.** Всё остальное наследует владельца через определение:

```
clients ─┬─< api_keys
         └─< process_definitions(client_id) ──< process_instances(client_id*) ──< activities/tokens/variables
                                                                              ├──< user_tasks / service_tasks
                                                                              ├──< incidents
                                                                              └──< timer_jobs / *_subscriptions
```

`client_id` денормализуем на `process_instances` (проставляется при старте из определения) — чтобы
фильтровать рантайм по одному столбцу без джойнов. Глубже (activities/tasks/incidents) фильтруем через
`process_instance_id IN (инстансы клиента)` — это уже умеют существующие спецификации (подзапросы).

---

## 3. Схема БД (новые таблицы/колонки)

- **`clients`**: `id`, `name`, `slug` (уник.), `active`, `created_at`.
- **`api_keys`**: `id`, `client_id`, `name`, `key_prefix` (8 симв., для идентификации), `key_hash`
  (PBKDF2/SHA-256 от полного ключа — **plaintext не храним**), `active`, `created_at`,
  `last_used_at`, `expires_at` (опц.). У клиента может быть несколько ключей (ротация).
- **`process_definitions.client_id`** (FK → clients, nullable на время миграции).
- **`process_instances.client_id`** (денормализация владельца).
- **`ui_users.client_id`** (nullable; NULL = супер-админ-скоуп).

Формат ключа: `zbpm_<keyId8>_<secret>` — по префиксу быстро находим запись, секрет сверяем с хэшем.
Полный ключ показываем **один раз** при создании.

### Изменения существующих ограничений
- Сейчас `process_definitions` уникальность по `(code, version)` **глобально**. С тенантностью —
  по `(client_id, code, version)`. Иначе два клиента не смогут иметь процесс с одинаковым key.
- `sha256` сейчас глобально уникален — сделать уникальным **в рамках клиента** (или убрать строгий
  uniqueness, оставив дедуп внутри клиента).

## 4. Точки enforcement

### 4.1 Резолв контекста (вход)
Новый `TenantContextFilter` (servlet-фильтр рядом с `JwtAuthFilter`):
1. Если есть API-ключ → найти по `key_prefix`, сверить хэш, проверить `active`/`expires_at` →
   `TenantContext{ clientId, CLIENT, role=CLIENT }`, обновить `last_used_at`.
2. Иначе если валидный JWT (UI-user) → `TenantContext{ user.client_id, UI, user.role }`.
3. Иначе аноним (для открытых эндпоинтов, пока tenancy выключен — см. флаг).
Контекст кладём в `ThreadLocal` (request-scoped), доступен сервисам/спецификациям.

### 4.2 Запись (владение)
- **Deploy** `POST /process-definitions`: проставляем `client_id = ctx.clientId`. Супер-админ —
  обязан указать целевого клиента (параметр), либо запрещаем.
- **Update/Delete/новая версия** определения: разрешено только если `definition.client_id == ctx.clientId`
  (иначе `403`). Супер-админ — всё.

### 4.3 Чтение/выполнение (изоляция)
Добавить предикат `client_id = ctx.clientId` (или `process_instance ∈ инстансы клиента`) во все
выборки `QueryServiceImpl` и стартовые проверки:
- `process-definitions`, `process-instances`, `user-tasks`, `service-tasks`, `incidents`,
  `variables`, `timer-jobs`, `message-subscriptions`, `activities`.
- `start instance`, `complete task`, `fail/resolve` — проверять принадлежность целевого объекта клиенту.
- **Корреляция message/signal** — критично: матчить только подписки **того же клиента** (иначе утечка
  между арендаторами). Сейчас матч по имени глобально → добавить `client_id` в подписки/матчинг.

> Реализация скоупинга: либо общий хелпер, добавляющий спецификацию по `client_id`, либо Hibernate
> `@Filter`, включаемый из `TenantContext`. Рекомендую явные спецификации (предсказуемо, уже есть паттерн).

## 5. Обратная совместимость

- Флаг **`zorrobpm.security.tenancy.enabled`** (по умолчанию `false`): выключено — поведение как сейчас
  (без скоупинга), Java-клиент и текущие интеграции не ломаются. Включаем осознанно.
- Миграция данных: создать **legacy-клиента** и проставить его `client_id` всем существующим
  `process_definitions`/`process_instances`. Без этого старые данные «осиротеют».
- Когда tenancy включён, но запрос без ключа/контекста → `401` на защищённых путях.

---

## 6. Связь с уже сделанным (UI-auth)

- `JwtAuthFilter`/`TokenService`/`ui_users` уже есть. `TenantContextFilter` — обобщение: добавляет
  ветку API-ключа и прокидывает `clientId` в общий контекст.
- `PasswordHasher` переиспользуем для хэша API-ключей.
- Управление клиентами/ключами — новые админ-экраны рядом с `Users` (только супер-админ).

## 7. Открытые решения (нужно подтвердить)

1. **UI-user ↔ client**: привязывать пользователя к одному клиенту (рекомендую) или у консоли всегда
   глобальный доступ, а тенантность только для API?
2. **Несколько клиентов на пользователя?** (MVP: один; later: членство M:N).
3. **Транспорт ключа**: `Authorization: Bearer` (конфликт с UI JWT — различать по префиксу `zbpm_`)
   или отдельный `X-API-Key` (чище). Рекомендую `X-API-Key`.
4. **Воркеры (RabbitMQ)**: джоб-канал внутренний и сейчас не тенантный. Нужна ли изоляция воркеров
   (отдельные очереди/тег клиента на джобе)? — выносим в отдельную фазу.
5. **Уникальность process key**: глобально запретить коллизии ключей между клиентами или разрешить
   (рекомендую разрешить — уникальность per client).

## 8. Примерный план работ (фазы)

| Фаза | Содержание | Объём |
|---|---|---|
| **0. Дизайн** | Подтвердить §7 (особенно user↔client, транспорт ключа, дефолт флага). | S |
| **1. Схема** | Миграции: `clients`, `api_keys`, `+client_id` в `process_definitions`/`process_instances`/`ui_users`; уник. `(client_id, code, version)`; seed legacy-клиента + бэкафилл. | M |
| **2. Клиенты и ключи** | Сущности/репо/сервис; `POST /clients`, `GET /clients`; `POST /clients/{id}/api-keys` (ключ показываем один раз), `DELETE` (revoke), список. Хэш ключа через `PasswordHasher`. Только супер-админ. | M |
| **3. Контекст запроса** | `TenantContextFilter` (API-ключ + JWT → `TenantContext` в ThreadLocal); резолв ключа по префиксу+хэш, `active/expires`, `last_used_at`. Флаг `tenancy.enabled`. | M |
| **4. Владение определениями** | Стамп `client_id` на deploy; guard update/delete/версии; скоуп списка/`{id}`/`xml`/`structure`. `403` на чужое. | M |
| **5. Изоляция рантайма** | `client_id` на старте инстанса; предикаты во всех `find*` (`QueryServiceImpl`) и проверки в start/complete/fail/resolve; **скоуп корреляции message/signal по client_id**. | L |
| **6. Уникальность/конфликты** | Уник. per-client (key+version, sha256), 409 при коллизии в рамках клиента. | S |
| **7. Фронтенд** | Экраны «Clients» и «API Keys» (супер-админ): создать клиента, выпустить/отозвать ключ (показ один раз), привязка UI-user к клиенту в Users. Колонка «owner» где уместно. Данные уже скоупятся API. | M |
| **8. Хардненинг/доки** | Ротация/срок ключей, `last_used`, аудит-лог выпуска/отзыва, тесты изоляции (клиент A не видит B), README/доки, опц. rate-limit по ключу. | M |
| **9. (Опц.) Воркеры** | Тенантная маршрутизация джобов в RabbitMQ (очереди/тег клиента), если нужна изоляция и на уровне исполнения. | L |

Критический путь для «клиент видит только своё»: фазы **1 → 3 → 4 → 5**. Фазы 2/7 — управление,
6/8/9 — хардненинг.

## 9. Риски

- **Утечка через корреляцию** message/signal/timer-start, если забыть скоуп (фаза 5) — главный риск изоляции.
- **N+1/перф** при джойнах на `client_id` — закрываем денормализацией на `process_instances` + индексами.
- **Java-клиент**: сейчас без ключа — до включения `tenancy.enabled` ничего не ломается; при включении
  клиенту нужно выдать ключ и слать его.
- **Миграция legacy-данных** — обязательный бэкафилл, иначе «осиротевшие» процессы станут невидимыми.
