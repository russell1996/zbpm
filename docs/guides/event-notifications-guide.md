# Уведомления о событиях ZorroBPM — полное руководство (с нуля)

> Цель документа: объяснить **предельно просто и по шагам**, как внешняя система узнаёт, что в движке
> что-то произошло (появилась задача, завершился процесс, поднялся инцидент), и как отфильтровать это
> «до конкретного сотрудника». Читай как будто ты видишь RabbitMQ впервые.
>
> Почти вся схема уже в проде (события, outbox, topic-exchange, обогащённый routing-key `process.<pdKey>...`,
> SSE-мост, assignee/candidateGroups в data, claim/unclaim/reassign с user-task.assigned/unassigned).

---

## Часть 0. Картина целиком (три действующих лица)

Представь почту.

1. **Движок (ZorroBPM)** — тот, кто **кричит факты**: «создана задача Approve в процессе vacation»,
   «инцидент поднялся», «процесс завершился». Движок **не знает**, кто его слушает, и знать не хочет.
2. **RabbitMQ (брокер)** — **почтовое отделение**. Движок бросает письмо в один ящик (`exchange`), а почта
   разносит копии по всем, кто оформил подписку с подходящим адресом.
3. **Потребитель** (твоя внешняя система / её бэкенд) — тот, кто **подписался** и слушает свой почтовый
   ящик (`queue`). Получив письмо, он сам решает, что с ним делать (например, показать нужному сотруднику).

Ключевая мысль, которую надо усвоить сразу:

> **Есть ДВА разных вопроса, и путать их нельзя.**
>
> - «**Покажи мне список моих задач**» — это **ЗАПРОС** (`GET /user-tasks?assignee=ivanov`). Источник
>   истины. Список НИКОГДА не собирают из событий.
> - «**Скажи, когда что-то изменилось**» — это **СОБЫТИЕ**. Оно лишь **пинг**: «эй, перечитай список».
>   Событие не носит в себе весь список — оно говорит «вот тут поменялось, сходи обнови».

Всё остальное в этом документе — про второй вопрос (события). Первый (список) уже готов эндпоинтом
`GET /user-tasks` с фильтрами `assignee`, `candidateGroup`, `completed` и т.д.

## Часть 1. Из чего состоит событие (конверт / envelope)

Каждое событие — это JSON-«конверт». Пример (задача создана):

```json
{
  "eventId": "8f3b...-uuid",              // уникальный id ЭТОГО письма — для дедупликации
  "sequence": 1024,                        // сквозной номер по порядку — для докачки (Контракт B)
  "type": "user-task.created",             // ЧТО произошло
  "version": 1,
  "occurredAt": "2026-07-20T10:00:00Z",
  "processDefinitionKey": "vacation",      // КАКОЙ процесс (человекочитаемый ключ)
  "processInstanceId": "...-uuid",         // КАКОЙ запуск процесса
  "elementId": "Approve",                  // КАКОЙ элемент BPMN
  "data": {                                // тип-специфичная нагрузка
    "activityId": "...-uuid",
    "assignee": "ivanov",                  // КОМУ назначено (ключа нет, если не назначена)
    "candidateGroups": "managers,admins"   // какие группы могут забрать — строка через запятую (не массив)
  }
}
```

Запомни разделение — оно объясняет вообще всё дальше:

| Часть конверта | Где живёт | Для чего |
|---|---|---|
| `type`, `processDefinitionKey`, `elementId` | попадают в **адрес письма** (routing-key) | чтобы почта разнесла письмо только тем, кому надо, **до доставки** |
| `assignee`, `processInstanceId`, значения переменных | живут **внутри** `data`/тела | по ним фильтруют **после** доставки, в коде потребителя |

Почему так — в Части 4. Пока просто прими: **процесс/элемент/тип — это адрес, сотрудник — это уже内容 письма.**

## Часть 2. Адрес письма (routing-key) — самое важное

Движок кладёт письмо в **один** topic-exchange с именем `zorrobpm.events` и вешает на него **адрес**
(routing-key). Адрес — это строка из сегментов через точку:

```
process.<processDefinitionKey>.<domain>.<action>[.<elementId>]
```

Разбор на примере `process.vacation.user-task.created.Approve`:

| Сегмент | Значение | Что означает |
|---|---|---|
| `process` | фиксированный префикс | «это событие процесса» |
| `vacation` | processDefinitionKey | процесс «Отпуск» |
| `user-task` | domain | речь про пользовательскую задачу |
| `created` | action | её создали (а не завершили) |
| `Approve` | elementId | конкретный элемент BPMN |

Другие примеры адресов:
```
process.vacation.user-task.completed.Approve
process.vacation.incident.raised.Approve
process.vacation.instance.started            (событие уровня процесса, элемента нет)
process.orders.user-task.created.Pack
```

### Почему именно такой порядок (процесс — слева)

В topic-адресах символ `*` заменяет **один** сегмент, `#` — **любой хвост**. Правило: **ту ось, по которой
чаще всего говоришь «дай мне ВСЁ под этим», ставь левее — тогда просто дописываешь `.#`.**

Самый частый потребитель — «я владею процессом vacation, дай мне всё про него». Поэтому процесс стоит слева,
и подписка на весь процесс выглядит чисто: `process.vacation.#`.

### Правило: что идёт в адрес, а что в тело

> **В адрес (routing-key) — только ОГРАНИЧЕННЫЕ и СТАБИЛЬНЫЕ вещи.**
> **Всё безграничное или меняющееся — в тело, фильтруется в коде.**

| Измерение | Ограниченное? | Куда | Почему |
|---|---|---|---|
| processDefinitionKey | да (десятки-сотни, стабилен между версиями) | **адрес** | можно биндиться заранее |
| domain (user-task/incident/…) | да | **адрес** | |
| action (created/completed/…) | да (2-3 значения) | **адрес** | бейдж «новые» ≠ аудит «завершённые» |
| elementId | да (элементы модели) | **адрес** | |
| **assignee (сотрудник)** | **НЕТ** (людей тысячи, назначение меняется) | **тело `data`** | нельзя завести адрес/очередь на каждого |
| processInstanceId | НЕТ (каждый запуск — новый) | **тело** | |

## Часть 3. Как подписаться — ПО ШАГАМ (для разработчика внешней системы)

Тебе нужно ровно две вещи в RabbitMQ: **своя очередь** (твой ящик) и **биндинг** (правило, какие адреса
в неё складывать). Делается это **один раз, при старте твоего сервиса**.

### Шаг 1. Пойми, что тебе вообще нужно ловить

Ответь на один вопрос: «события каких процессов / каких типов мне интересны?». От ответа зависит биндинг:

| Тебе нужно… | Биндинг (binding key) |
|---|---|
| всё про процесс `vacation` | `process.vacation.#` |
| только созданные задачи в `vacation` | `process.vacation.user-task.created.#` |
| все задачи (любой action) в `vacation` | `process.vacation.user-task.#` |
| конкретный элемент `Approve` | `process.vacation.user-task.created.Approve` |
| все инциденты по всем процессам | `process.*.incident.#` |
| вообще всё | `process.#` |

Для кейса «сотрудник хочет свои задачи» типовой ответ — `process.vacation.user-task.#` (или `.created.#`).
Сотрудника здесь НЕТ — он фильтруется потом (Часть 4).

### Шаг 2. Объяви durable-очередь (свой ящик)

`durable` = «переживает перезапуск брокера». Важно: **durable-очередь копит письма, даже пока твой сервис
лежит.** Объявил один раз — окна потерь больше нет.

```java
// Spring AMQP — объявляется бином при старте
@Bean Queue myUserEventsQueue() {
    return QueueBuilder.durable("myapp.user-events").build();
}
```

### Шаг 3. Привяжи очередь к exchange нужным адресом (биндинг)

```java
@Bean TopicExchange zorroEvents() {
    return new TopicExchange("zorrobpm.events", true, false);   // тот же exchange, что и у движка
}

@Bean Binding myBinding(Queue myUserEventsQueue, TopicExchange zorroEvents) {
    return BindingBuilder.bind(myUserEventsQueue)
            .to(zorroEvents)
            .with("process.vacation.user-task.#");              // ← твой интерес из Шага 1
}
```

Нужно несколько интересов — сделай несколько биндингов на ту же очередь (`process.vacation.user-task.#` +
`process.orders.user-task.#` и т.д.).

### Шаг 4. Слушай очередь и ОБЯЗАТЕЛЬНО делай дедупликацию

Доставка **at-least-once** (гарантия «хотя бы один раз») — одно и то же письмо может прийти **дважды**.
Поэтому храни виденные `eventId` (например, в Redis/таблице) и повтор игнорируй:

```java
@RabbitListener(queues = "myapp.user-events")
public void onEvent(EventEnvelope e) {
    if (alreadyProcessed(e.getEventId())) return;   // дедуп по eventId — обязательно
    handle(e);
    markProcessed(e.getEventId());
}
```

### Шаг 5. Когда подписываться и что делать с пропущенным

- **Когда:** один раз, при старте сервиса (Шаги 2-3). Не «когда сотрудник зашёл», не «когда процесс
  задеплоили». Просто на старте.
- **Задеплоили новый процесс в движке?** Если ты биндился с `#` (напр. `process.*.user-task.#`) — новые
  процессы ловятся **сами**, ничего менять не надо.
- **Твой сервис лежал дольше, чем очередь хранит письма (или ты только что развернулся с нуля)?** Догони
  пропущенное **запросом** (Контракт B): `GET /events?since=<последний_известный_sequence>`. То есть
  подписка — статический конфиг, а «дыры» закрывает курсор.

**Итого подписка = 3 бина (очередь + exchange + биндинг) один раз при старте. Всё.**

## Часть 4. Фильтрация по сотруднику (assignee) — максимально подробно

Это самый частый вопрос и самое непонятное место. Читай медленно.

### Почему нельзя просто «подписаться на задачи Иванова» в брокере

Три причины, каждая достаточна:
1. **Сотрудников неограниченно.** Заводить адрес/очередь на каждого — это тысячи очередей, брокер ляжет.
2. **Назначение меняется.** Сегодня задача на Иванове, завтра он её вернул в пул, забрал Петров. Адрес
   письма фиксируется в момент отправки — он не умеет «следовать» за назначением.
3. **Задача часто вообще без конкретного человека.** Она создаётся на **группу** (`candidateGroups:
   ["managers"]`), и её «видят» все менеджеры сразу. У письма нет одного assignee.

Вывод: **брокер работает на уровне процесса (это ограниченная ось), а «кому из людей показать» —
разбирает ПОСЛЕДНИЙ ХОП: твой бэкенд, который знает, кто сейчас онлайн.**

### Что для этого держит твой бэкенд (BFF)

Две своих таблички в памяти (движок про них не знает):
- **карта сессий:** `userId → его открытые WebSocket-соединения` (кто сейчас залогинен и смотрит в браузер);
- **членство в группах:** `userId ↔ candidateGroup` (из твоей системы пользователей).

### Пошаговый алгоритм (сотрудник Иванов заходит и хочет свои задачи)

**Подготовка (один раз, при старте бэкенда):**
- **P1.** Объявил очередь + биндинг `process.*.user-task.#` (Часть 3). Теперь ты получаешь ВСЕ события
  пользовательских задач по всем своим процессам — но пока не знаешь, кому их показывать.

**Когда Иванов открывает интерфейс:**
- **U1.** Иванов логинится → его браузер открывает WebSocket к твоему бэкенду → бэкенд записывает
  `ivanov → эта сессия` в карту сессий.
- **U2.** Браузер грузит текущий список: `GET /user-tasks?assignee=ivanov&completed=false` → рисует задачи.
  Это **истина** (включая задачи, созданные до того, как Иванов зашёл).

**Когда где-то в движке создаётся задача (в любой момент):**
- **E1.** Движок эмитит `user-task.created` → outbox → `zorrobpm.events` с адресом
  `process.vacation.user-task.created.Approve` → письмо падает в твою очередь `myapp.user-events`.
- **E2.** Твой `@RabbitListener` получил письмо. Дедуп по `eventId`.
- **E3.** Бэкенд смотрит в тело и вычисляет **множество заинтересованных сотрудников**:
  - если `data.assignee` задан → `{ "ivanov" }`;
  - иначе разворачивает `data.candidateGroups` (строка через запятую) в членов групп → напр. `{ все managers }`.
- **E4.** Пересекает это множество с картой сессий (кто из них **сейчас онлайн**). Для Иванова находит его
  WebSocket.
- **E5.** Пушит Иванову в его WebSocket **крохотное** сообщение: `{action:"task-created", taskId,
  processInstanceId}`. (Только сигнал, не весь список!)
- **E6.** Браузер Иванова получил пуш → **не доверяет ему как данным** → перезапрашивает
  `GET /user-tasks?assignee=ivanov&completed=false` (или патчит одну строку) → список обновился вживую.

Ещё раз, что тут произошло: **брокер отдал событие уровня процесса; твой бэкенд сузил его до «Иванов»
своим знанием assignee + карты сессий; браузер подтвердил запросом.** assignee в брокере не участвовал.

### Тонкость с пулом и claim (иначе список «протухает»)

- Задача создана на группу (`candidateGroups: ["managers"]`, assignee пуст) → по E3 её видят ВСЕ онлайн-
  менеджеры — правильно.
- Один менеджер **забрал** задачу (claim) → у остальных она должна **исчезнуть**. Движок эмитит
  `user-task.assigned` (кто-то стал assignee) — см. `user-task.assigned` в каталоге событий.

### Для нашего встроенного SPA (без своего бэкенда) — через SSE

Тот же принцип, но «последний хоп» — наш SSE-мост (Контракт C). Тогда SPA:
1. грузит `GET /user-tasks?assignee=me&completed=false`;
2. открывает `new EventSource('/events/stream?processInstanceId=<Y>')` (или по типу) и на событие
   перечитывает/патчит.

**Важно для безопасности:** если добавляем в SSE фильтр `?assignee=`, значение брать из
**аутентифицированного пользователя**, а не из свободного параметра (иначе Петров подпишется
`?assignee=ivanov` и увидит чужое).

## Часть 5. Три способа получать события (контракты) — когда какой

| Контракт | Что это | Кому |
|---|---|---|
| **A — AMQP** (`zorrobpm.events`) | подписка на очередь RabbitMQ (Части 2-3) | внешние системы со своим бэкендом; надёжно, масштабируемо |
| **B — HTTP pull** (`GET /events?since=cursor`) | «дай всё, что случилось после курсора» | любой, кто не хочет AMQP; **докачка** пропущенного |
| **C — SSE push** (`GET /events/stream`) | сервер сам шлёт события в браузер (одностор.) | внешние UI и наш встроенный SPA |

Правило выбора: **система-система с очередью → A** (+ B для докачки). **Браузер → C** (через свой бэкенд или
напрямую наш SPA). B — универсальный запасной для всех.

## Часть 6. Что уже есть в проде, а что доделывается (честная граница)

**Уже работает:**
- таблица `events` (append-only, `sequence`), запись событий в outbox в той же транзакции (at-least-once);
- topic-exchange `zorrobpm.events`;
- каталог событий: `process-instance.started/completed/cancelled`, `activity.completed`,
  `user-task.created/completed`, `service-task.created`, `incident.raised/resolved`;
- **обогащённый routing-key** `process.<pdKey>.<type>[.<elementId>]` + `processDefinitionKey` в конверте +
  санитизация (EVT-7) — можно биндиться `process.vacation.#`;
- запрос-снапшот `GET /user-tasks?assignee=…` со всеми фильтрами;
- Контракт B (`GET /events`) с authz по grants;
- **Контракт C** — SSE-мост `GET /events/stream` + `EventAuthzResolver` (authz DENY-by-default) + фронт-
  интеграция `handleEvent` в Pinia-сторах (EVT-4/EVT-5).

**Выполнено:**

| WO | Что | Статус |
|---|---|---|
| **EVT-8a** | добавить в `data` события `assignee`, `candidateGroups` | ✅ В проде |
| **EVT-8b** | эмитить `user-task.assigned`/`unassigned` при claim/reassign | ✅ В проде (INT-5) |

> Состояние конверта в коде: [DomainEventEmitter.java](../../zorrobpm-engine/src/main/java/com/zorrodev/bpm/engine/event/DomainEventEmitter.java)
> кладёт `eventId, type, occurredAt, processInstanceId, processDefinitionId, processDefinitionKey, elementId, data`.
> assignee и candidateGroups в `data` — EVT-8a. user-task.assigned/unassigned — INT-5.

## Шпаргалка (TL;DR)

1. **Список задач — запросом** `GET /user-tasks?assignee=ivanov`. Событие — только пинг «перечитай».
2. **Подписка = 1 очередь + биндинг**, один раз при старте: `process.vacation.user-task.#`.
3. **Адрес события** = `process.<pdKey>.<domain>.<action>.<element>`. Всё ограниченное — в адрес.
4. **assignee — НЕ в адрес.** Он в `data`; кому показать — решает твой бэкенд по assignee + карте сессий.
5. **Дедуп по `eventId`** обязателен (at-least-once). Пропущенное догоняешь `GET /events?since=cursor`.
