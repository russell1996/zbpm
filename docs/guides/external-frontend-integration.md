# Интеграция внешнего фронта с движком

> Для кого: команда, которая пишет СВОЙ браузерный UI (не встроенный SPA ZorroBPM) поверх старт-форм и
> задач движка — например, внешняя система, использующая ZorroBPM как headless-BPM-бэкенд.
> Если вместо браузера у тебя backend-сервис со своим RabbitMQ-потребителем — тебе не сюда, а сразу в
> [event-notifications-guide.md](event-notifications-guide.md) (Контракт A).
>
> База: [ADR-7](../adr/ADR-7-event-notification-architecture.md) — вся событийная архитектура. Этот
> документ — практический маршрут поверх неё, для одного конкретного случая: браузер запускает процесс
> со старт-формы и должен понять, что произошло дальше.

## Модель: два независимых канала

1. **Команды** (запись) — обычный синхронный REST. Старт процесса, complete задачи. Ответ говорит только
   «команда принята», не «бизнес-результат готов».
2. **Realtime** (чтение состояния) — событие-пинг «что-то изменилось» + отдельный GET за актуальными
   данными. Событие никогда не несёт весь список/сущность целиком.

Не смешивай их: не жди бизнес-результат в ответе на старт, не пытайся собрать состояние из данных события.

---

## Шаг 1 — Старт процесса из формы

```
GET  /process-definitions/{key}/start-form     → схема формы (form-js JSON) для рендера
POST /process-instances                        → { processDefinitionKey | processDefinitionId, variables }
```

Ответ `POST /process-instances` — `{ id: <processInstanceId> }`. Это **command-ack**, не результат:
процесс только начал выполняться, первый сервис-таск (если он есть сразу после старта) ещё не отработал.
`processInstanceId` из этого ответа — твой ключ корреляции для всего, что дальше.

## Шаг 2 — Аутентификация

`POST /auth/login` → `{ token, ... }`, а также httpOnly-cookie `zbpm_token`. Дальше — `Authorization:
Bearer <token>` (приоритет) либо cookie (fallback), см. `JwtAuthFilter.java`.

**Важный технический нюанс, если фронт на другом домене/origin:** нативный браузерный `EventSource`
(на нём построен Контракт C, Шаг 3) **не умеет** отправлять произвольные заголовки — значит `Authorization:
Bearer` для SSE-соединения физически недоступен. Query-параметра с токеном как обхода **в этом эндпоинте
не реализовано**. Рабочие варианты:

- same-origin/reverse-proxy — cookie `zbpm_token` уходит с SSE-запросом сама, ничего доп. делать не надо;
- честный cross-origin без общего домена — SSE (Контракт C) не заведётся, используй Контракт B
  (`GET /events?since=cursor`, обычный fetch с Bearer-заголовком) поллингом.

Проверь свою топологию ДО того, как проектировать realtime — это решает, доступен ли тебе Контракт C
вообще.

## Шаг 3 — Realtime: подписка на процесс

Если SSE доступен (см. Шаг 2) — открой сразу после ответа на старт:

```
GET /events/stream?processInstanceId=<id полученный на Шаге 1>
```

`EventSource` в браузере сам держит соединение и реконнектится (`Last-Event-ID` уходит автоматически при
разрыве — докачка пропущенного). Работай на этом канале, не опрашивай `GET /events` параллельно — это
просто лишняя нагрузка без пользы, пока SSE жив.

`GET /events?since=<sequence>&processInstanceId=<id>` (Контракт B) — держи как:
- единственный вариант, если SSE недоступен (Шаг 2);
- разовый catch-up после того, как `EventSource.onerror` не может законнектиться подряд, либо после
  долгого простоя (вкладка была закрыта часами).

Оба контракта — **at-least-once**: дедуплицируй по `eventId`.

## Шаг 4 — Как понять, что случилось с конкретным шагом

Полный каталог типов событий и состав `data` — [event-catalog.md](event-catalog.md). Здесь — то, что
нужно знать именно для корреляции с шагом процесса, который ты ждёшь (например, сервис-таск сразу после
старт-формы).

Ты заранее знаешь **какой шаг** ждёшь — это часть контракта с тем, кто пишет BPMN-процесс (как имя
REST-эндпоинта, не угадывается рантаймом). У события есть два поля-кандидата на это сравнение:

- **`elementId`** — id элемента с BPMN-диаграммы. Есть у ЛЮБОГО события (user-task, gateway,
  process-instance и т.д.), но это диаграммный артефакт: может тихо измениться при редактировании
  процесса в редакторе. Работает СЕГОДНЯ, для всех типов элементов.
- **`data.job`** — стабильное имя джоба сервис-таска (то же, чем роутится очередь воркера), аналог
  `zeebe:taskDefinition type` у Camunda 8/Zeebe — намеренно не связано с диаграммным id, переименование
  элемента на него не влияет. **Только для сервис-тасков.** Статус: заведено
  ([WO-EVT-9](../../governance/workorders/WO-EVT-9-service-task-job-in-events.md)), в очереди, ещё не в
  master — до мержа ориентируйся на `elementId`, дальше можно переключиться на `data.job` там, где шаг —
  сервис-таск (`elementId` при этом никуда не денется, оба поля сосуществуют).

## Шаг 5 — Успех или провал

Для шага, который отработал (сервис-таск или любой другой), долетит один из двух типов — третьего не
будет:

| Событие | Что значит | `data` |
|---|---|---|
| `activity.completed` | шаг выполнился успешно | `{}` (для сервис-таска — плюс `job`, после WO-EVT-9) |
| `incident.raised` | шаг окончательно провалился (ретраи исчерпаны) | `{ incidentId, message }` (плюс `job`, после WO-EVT-9) |

**Между стартом и одним из этих двух может быть тишина.** Если сервис-таск временно упал, но у него
остались ретраи — движок тихо передиспатчит джоб тому же воркеру, никакого события не будет. Событие
приходит только на финал (успех или окончательный провал), не на каждую попытку. Это ожидаемое поведение
движка, не потеря событий на твоей стороне.

На `activity.completed` — не ищи бизнес-данные в `data` (там пусто), перечитай сущность обычным GET. На
`incident.raised` — `data.message` уже содержит текст ошибки от воркера, можно показать пользователю как
есть.

## Чего не делать

- Не жди результат в ответе на `POST /process-instances` — это только ack.
- Не реконструируй список/состояние из `data` события — событие только повод перечитать через GET.
- Не полли `GET /events` постоянно параллельно с живым SSE — лишняя нагрузка без пользы.
- Не зашивай во фронт диаграммные детали сверх elementId/job конкретного ожидаемого шага — остальное
  (структура процесса, порядок шагов) может меняться, фронт не должен на это опираться.
