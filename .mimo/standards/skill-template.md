# Skill Template — нормативная структура карточки роли

Любая карточка скилла в [../skills/](../skills/) ДОЛЖНА следовать этой структуре. Инженерные роли
ОБЯЗАНЫ включать секцию «Anti-imitation invariants» (ссылка на [V1–V10](../rules/rules.md)).

```markdown
# <Role Name>

## Role
Кто это и зачем в команде (1–2 предложения).

## Mission
Главная цель роли в терминах продукта ZBPM.

## Responsibilities
- Что роль делает (буллеты).

## Authority
Что роль ВПРАВЕ решать/менять сама.

## Forbidden
Что роль НЕ делает (границы; для инженеров — что не трогать без ADR/одобрения).

## Required (inputs)
Что нужно на входе (артефакты, доступы, контекст).

## Rules
Профильные правила + ссылка на общие [rules](../rules/rules.md).

## Anti-imitation invariants   ← обязательно для инженерных ролей
Какие из V1–V10 особенно критичны для этой роли и как они проверяются здесь.

## Review checklist
Что проверяет ревьюер у работы этой роли (объективно).

## Quality gates
Какие гейты ([quality-gates](../quality-gates/gates.md)) роль обязана пройти.

## Acceptance
Объективные критерии «работа роли выполнена».

## Input / Output artifacts
Вход → Выход (ADR, PR, тест-репорт, бенч, миграция, …).

## Interaction
С кем взаимодействует (хэндофы, кому эскалирует).

## Prompts
Ссылки на [prompts](../prompts/): system / task / review / validation / escalation / handoff.
```

## Правила заполнения
- Никаких «вода-обязанностей»: каждая строка проверяема или отбрасывается.
- Acceptance всегда механический (grep/тест/замер), не «на глаз».
- Для ZBPM-специфичных ролей — привязка к конкретным классам/модулям ([analysis](../../docs/analysis/README.md)).
