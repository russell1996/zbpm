# Правила Mimo — V1–V10

Эти правила действуют в **каждой** задаче, без исключений.

| # | Правило | Метод верификации | Запрещено |
|---|---|---|---|
| **V1** | Верифицируй по диску, а не по словам | `grep / find / run` — код должен быть в файле и вызываться по живому пути | Говорить "сделано" без файла на диске |
| **V2** | Критерии приёмки — объективно, команда→факт | Каждый критерий = команда + ожидаемый вывод | Субъективные критерии ("код выглядит правильно") |
| **V3** | Proof-of-failure обязателен | Показать IT/тест КРАСНЫМ до фикса, ЗЕЛЁНЫМ после | Сдавать зелёный тест без доказательства что он был красным |
| **V4** | Не отключай тесты | Запрещено `@Disabled`, `skip`, ослабление assert-ов | Делать тест зелёным через его отключение |
| **V5** | Символ в файле ≠ готово | Код должен вызываться из живого пути (вызов из main-flow, IT проверяет) | Добавить класс без вызова и сдать как "реализовано" |
| **V6** | Симуляция ≠ конкурентность | Конкурентный тест = 2 реальных потока / транзакции одновременно | Эмулировать race sequential-вызовами |
| **V7** | Не трогай scope | Только файлы из WO-scope. Прочее — отдельный WO | Рефакторить "заодно" вне scope |
| **V8** | Одна задача одновременно | Работа по одному WO за раз | Брать 2 WO параллельно |
| **V9** | Честный "не смог" > имитация | Если не получилось — "НЕ СДЕЛАНО: причина" в отчёте | Сдавать половинчатую реализацию как полную |
| **V10** | Структурное изменение → ADR сначала | ADR согласован → код. Без ADR — нет кода | Писать structural-изменение без ADR |

## Git workflow (обязателен)

### После завершения каждой задачи
```bash
# 1. Создать ветку (если ещё нет)
git checkout -b feature/WO-XXX-краткое-описание

# 2. Добавить только файлы из scope WO (не git add -A!)
git add <конкретные файлы>

# 3. Проверить что стейджинг правильный
git status

# 4. Коммит
git commit -m "feat(WO-XXX): краткое описание что сделано

- критерий 1: команда → факт
- критерий 2: команда → факт
proof-of-failure: <название теста> был RED, стал GREEN

Co-Authored-By: Mimo <mimo@zorrodev.com>"

# 5. Push
git push -u origin feature/WO-XXX-краткое-описание
```

### Формат commit message
```
<тип>(WO-XXX): <что сделано> (imperative mood)

<необязательно: детали>

Co-Authored-By: Mimo <mimo@zorrodev.com>
```
Типы: `feat` / `fix` / `test` / `refactor` / `perf` / `chore`

### Запрещено
- `git add -A` или `git add .` — только конкретные файлы (риск стейджинга секретов/лишнего)
- `git push --force` без согласования CTO
- `git commit --no-verify`
- Коммит в `master` напрямую — только через PR

## Всегда (в каждом PR)

- Отчёт по шаблону DoD: таблица критерий → команда → факт
- IT на зелёном перед merge: `mvn clean verify` → BUILD SUCCESS
- Proof-of-failure показан явно (лог или скриншот КРАСНОГО теста)
- Scope не расширен (только файлы из WO)

## Никогда

- `--no-verify` на commit
- `@Disabled` / `assumeTrue(false)` чтобы скрыть проблему
- "работает локально" без IT
- `git push` в master без review CTO
- Структурное изменение без ADR (замена алгоритма, схема DB без changeset, смена contract)

---

## Эскалация

Если правило создаёт конфликт с задачей → **эскалировать CTO**, не делать самостоятельно.  
Примеры: "scope слишком маленький чтобы исправить правильно", "нужен ADR но WO его не упоминает".
